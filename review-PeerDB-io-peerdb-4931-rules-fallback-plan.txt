## Issue summary

Long-running standalone QRep mirrors stop opening their detail page once `peerdb_stats.qrep_partitions` grows large. `POST /v1/mirrors/status` with `includeFlowInfo: true` returns HTTP 429 and gRPC code 8, `received message larger than max (12202405 vs. 4194304)` (a second mirror was `14857725` bytes, about 164k and 197k partition rows). The UI maps every failed status fetch to "We were unable to fetch details of this mirror" via `ui/app/mirrors/[mirrorId]/page.tsx` and `error.tsx`. Non-CDC `MirrorStatus` calls `qrepFlowStatus` → `getPartitionStatuses`, whose SELECT returns every row for `flow_name` with no `ORDER BY` or `LIMIT`, and `setupGRPCGatewayServer` dials the API with grpc-go's default 4 MiB receive cap. Replication keeps running; `includeFlowInfo: false` still returns `STATUS_RUNNING`. A contributor pointed at the README deprecation of standalone QRep and suggested CDC plus ELT. This plan keeps that mirror type unchanged and only bounds the status read that makes the existing detail page fail.

## Approach

In `getPartitionStatuses`, keep the same five columns and the `flow_name=$1` predicate, and return at most 10000 rows: `ORDER BY start_time DESC NULLS LAST, id DESC LIMIT 10000`. Store that SQL in a package-level string in `flow/cmd/mirror_status.go` that `getPartitionStatuses` executes, with the limit as a named constant interpolated the same way `CDCBatches` interpolates its integer limit. 10000 UUID-sized `PartitionStatus` values (partition ids are `uuid.NewString()`) stay under 1 MiB, while the reported 164k-row payload is about 12 MiB. `qrepFlowStatus` already embeds the slice on `QRepMirrorStatus`, and the detail page only draws a 10-row table plus the last 30 graph buckets, so the page loads without a new RPC. Leave catalog rows, replication, protos, `setupGRPCGatewayServer`, and the UI as they are. XMIN uses this same non-CDC status path and gets the same cap. Ship no version gate: mirror config and replicated rows stay the same, and preserving the unbounded payload preserves the failure.

## Test scenarios

- Regression test: add `TestQRepPartitionStatusQueryIsBounded` in `flow/cmd/mirror_status_test.go` (`package cmd`, no `//go:build tilt`, no database). It reads the SQL string `getPartitionStatuses` executes and fails while that query has no `LIMIT`. Assert it contains `flow_name=$1`, `ORDER BY start_time DESC NULLS LAST`, `id DESC`, and `LIMIT` with the 10000 constant. Build one `PartitionStatus` with a 36-byte id, both timestamps set, and both int64 fields at `math.MaxInt64`; assert `proto.Size` of a `QRepMirrorStatus` repeated to the cap is under 4194304, and the same shape repeated 164000 times is at least 4194304. Run `cd flow && go test ./cmd/ -count=1 -run TestQRepPartitionStatusQueryIsBounded` (flow unit tests already compile this package against generated protos, as in `.github/workflows/flow.yml`). Observed result of that command is in Verification below: it passed, and the same `PartitionStatus` shape measures 800000 bytes at 10000 rows and 13120000 bytes at 164000 rows.
- Happy path: a mirror with fewer than 10000 partition rows still returns every row, newest `start_time` first, with the same five fields.
- Edge: rows with NULL `start_time` (inserted before `UpdateStartTimeForPartition`) sort after dated rows, so unstarted rows do not fill the window. The in-progress partition has `start_time` set and stays inside a full window. Equal `start_time` values break ties by `id DESC`.
- Error path: query and scan failures still return the existing `unable to query qrep partition` / `unable to scan qrep partition` errors. History past the cap returns the newest window instead of the gateway `ResourceExhausted` response.

## Verification

How the problem was established: issue https://github.com/PeerDB-io/peerdb/issues/4931 reports `POST /v1/mirrors/status` with `includeFlowInfo: true` failing as HTTP 429 / gRPC code 8, `received message larger than max (12202405 vs. 4194304)`, and a second mirror at 14857725 bytes. On this checkout, `git diff main...HEAD -- flow/cmd/mirror_status.go` shows the previous `getPartitionStatuses` query was `SELECT partition_uuid,start_time,end_time,rows_in_partition,rows_synced FROM peerdb_stats.qrep_partitions WHERE flow_name=$1` with no `ORDER BY` and no `LIMIT`. `setupGRPCGatewayServer` in `flow/cmd/api.go` dials with `grpc.NewClient` and does not set a receive limit, so grpc-go's default 4194304-byte cap still applies. This environment has no PeerDB catalog, Docker, or Tilt stack, so that HTTP 429 was not replayed against a live mirror.
